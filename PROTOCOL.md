# PROTOCOL: same-machine head-to-head, Qwen3.6-35B-A3B on one DGX Spark (bar P0)

Predeclared before any timed run. This file is committed and pushed before the first arm starts; any
later change to it is a separate, dated commit listed in section 10, and results say which protocol
commit they were taken under.

## 1. Question

On one DGX Spark (GB10, sm_121, driver 580.173.02, 121 GiB unified LPDDR5x), serving the same model
to the same prompts over the same HTTP API, how do three stacks compare **end to end**?

- **OURS**: `aien-serve-http`, binary `bin-19173f9e`, run from its directory with the live cmdline.
- **VLLM**: vLLM `0.29.0+5013de39.dev` from NVIDIA's NGC container `nvcr.io/nvidia/vllm:26.09-py3`,
  digest `sha256:557747337846eecf34486866f3d992383c6f8af869fdb0e365b5093fcaee02c2` (torch
  2.14.0a0 nv26.09, CUDA 13.4), pulled with `docker pull`; no system install.
- **LLAMA**: llama.cpp `b11913` (commit `7aca0d2ea8d92b56911233b822db01f9fbb1ae50`), the
  ggml-org CI release asset `llama-b11913-bin-ubuntu-cuda-13.4-arm64.tar.gz` (sha256 `55ee2ae4…18f4`)
  run with its companion `cudart-llama-b11913-bin-ubuntu-cuda-13.4-arm64.tar.gz` (sha256
  `f6a5a023…599a`) first on `LD_LIBRARY_PATH`. The release carries sm_121a machine code.

Every number in this repo is end to end: an HTTP client on the same host, timestamps taken in the
client. **No chip-only number (kernel time, GPU timer, per-launch microbenchmarks) appears in the
results table.** Numbers from other repos are not mixed in.

## 2. Model and weights

- Checkpoint: `Qwen/Qwen3.6-35B-A3B-FP8` revision `95a723d08a9490559dae23d0cff1d9466213d989`,
  local `~/models/qwen3.6-35b-a3b-fp8-95a723d0`, sha256 list `qwen3.6-35b-a3b-fp8-95a723d0.sha256`
  (56 files verified 2026-10-20). FP8 e4m3, block-wise scales, dynamic activation scales.
- OURS and VLLM load this folder directly (read-only).
- LLAMA cannot load safetensors. A GGUF is converted from **the same folder** with
  `convert_hf_to_gguf.py` at the same llama.cpp commit, `--outtype q8_0`.
  **Quantization difference, labeled on every LLAMA row:** Q8_0 (int8, one fp16 scale per 32
  weights, FP8 weights dequantized first and re-quantized) is not the FP8 e4m3 block-128 format the
  other two arms run. Agreement numbers against LLAMA therefore mix engine and quantization effects.
  If the converter refuses the FP8 checkpoint, LLAMA is NOT_RUN with the converter error quoted; no
  GGUF from other weights (e.g. a third-party GGUF) is substituted.
- Text only. Vision tower and MTP heads are not used by any arm (no speculative decoding anywhere).

## 3. API and request shape (identical for all arms)

`POST /v1/chat/completions`, one user message, `stream: true`,
`stream_options.include_usage: true`, `temperature: 0`, `top_p: 1`, `seed: 0`,
`chat_template_kwargs.enable_thinking: false` (OURS also runs `--thinking off`).
The client is `bench/bench.py` (Python 3 stdlib, `http.client`, one thread per stream, a barrier
releases concurrent streams together). One JSON row per request is written to `results/raw/`.

Timestamps (client `time.monotonic()`): `t_send` before the request is written; `t_first` at the first
SSE chunk carrying non-empty `content` or `reasoning_content`; `t_last` at the last such chunk.
Token counts come from the server's `usage` (prompt_tokens, completion_tokens). If an arm reports no
usage, the count is re-derived by tokenizing the returned text with the checkpoint's
`tokenizer.json` and the row is labeled `count=retokenized`.

## 4. Prompts (`prompts/`, generated by `bench/make_prompts.py`, committed before runs)

- `decode.jsonl`: 16 distinct short instructions asking for long prose (≈30-60 prompt tokens).
- `prefill.jsonl`: three documents of deterministic synthetic prose (seeded generator) plus one
  closing question, calibrated with the checkpoint tokenizer so that the **chat-rendered** prompt is
  ≈256, ≈2048, ≈8192 tokens. Actual `prompt_tokens` are reported per arm.
- Agreement reuses `decode.jsonl` (all 16).

## 5. Metrics

| ID | Metric | Cell | Definition |
|----|--------|------|------------|
| M1 | TTFT | decode c=1 | `t_first - t_send`, short prompt |
| M2 | decode tok/s, 1 stream | decode c=1, max_tokens 256 | `(completion_tokens - 1) / (t_last - t_first)` |
| M3 | decode tok/s at 4/8/16 concurrent | decode c=4/8/16, max_tokens 256 | per batch: aggregate = `sum(completion_tokens) / (max(t_last) - min(t_send))`; also per-stream M2 |
| M4 | prefill tok/s at 256/2k/8k | prefill, max_tokens 1, nonce prefix | `prompt_tokens / (t_first - t_send)` (end-to-end: includes HTTP, template, tokenizer, first sampled token) |
| M5 | peak memory | whole arm session | `MemAvailable(baseline, before launch) - min(MemAvailable during session)` from `/proc/meminfo` at 1 Hz; plus peak summed `VmRSS` of the server process tree (host-side view; on GB10 device allocations are system memory) |
| M6 | output agreement | agree c=1, 16 prompts, max_tokens 128 | per prompt, tokenize both outputs with `tokenizer.json`; matched = common-prefix length; rate = Σ matched / Σ max(len_a, len_b); also count of byte-identical outputs out of 16; pairs OURS–VLLM, OURS–LLAMA, VLLM–LLAMA; plus within-arm R1 vs R2 |

A nonce line (`Request id <uuid>. Ignore this line.`) is prepended to every prefill prompt so that no
arm's prefix cache can hit. Decode prompts carry no nonce (they are short; prefix caching of 40 tokens
does not change decode rate; TTFT on a repeated short prompt is labeled as such in M1).

Concurrency is what the arm is configured for as deployed: OURS runs the live `--batch-slots 8`. At
c=16, OURS refuses requests beyond 8 with HTTP 503 `server_busy` ("retry shortly"); the client
retries those every 50 ms with the clock running from the first send (amendment A1), and the retry
count is stored per row. That is part of the end-to-end result and is stated beside it.

## 7. Schedule, repetitions, statistics

- Two rounds, interleaved by arm: **R1 = OURS, VLLM, LLAMA; R2 = LLAMA, VLLM, OURS.**
- One model in memory at a time. Between arms: server stopped, process gone, `nvidia-smi
  --query-compute-apps` empty, MemAvailable back to within 2 GiB of the pre-launch baseline.
- Per arm session, cells in this order, each with **2 warmup batches then 3 measured batches**:
  decode c=1, c=4, c=8, c=16; prefill 256, 2k, 8k. Then the agreement cell (16 prompts, once each,
  no warmup). So each timing cell has 6 measured batches per arm across R1+R2.
- Reported per cell: **median and IQR** over the measured values (6 batch values for aggregate
  metrics; all per-stream values for per-stream metrics, count stated). Computed with Wolfram
  Language `Median` and `InterquartileRange` (Wolfram's default quartile definition); the query and
  result are kept in `results/wolfram/`. If the Wolfram MCP is not mounted, only exact counts and the
  raw rows are published and the table says so.
- No significance tests. A difference is called a win/loss only when the IQRs do not overlap;
  otherwise "overlapping".

## 8. Load and GPU-lock gates

- Timing cells run only when `load1 < 4` at cell start. The harness waits (polling 15 s) before each
  cell. `load1` at start and end is stored in every row. A row with `load1_start >= 4` (should the
  gate be overridden by a timeout) is published but excluded from the headline table and labeled
  LOADED.
- GPU: each arm session runs inside `flock -w 900 /tmp/aien-gb10.lock`, at most 60 minutes, with
  BOARD lines at START, T-5 (55 min) and END. The harness kills its own server at 60 min.
  No module reloads, no reboots, `/dev/nvidia-modeset` is never opened by the harness.
- An arm that cannot start (unsupported model, OOM, converter refusal) is recorded NOT_RUN with the
  exact error and log; it is not retried with different weights.
